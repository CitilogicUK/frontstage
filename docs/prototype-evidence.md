# Frontstage prototype evidence

The AI App Governance Platform spec describes four phases. Frontstage demonstrates workflows from all four with synthetic data. Use the local reviewer profile for the demo and record the deployed evidence separately for each pilot gate.

## Demo walkthrough

| Workflow                                | What to verify                                                                                                                                                                                                                                                                                                      |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Register proportionately                | Download a starter for software built with AI but with no runtime model, then register a proof of concept. Compare its path with a Tier 3 app that takes actions and requires human approval evidence. [Gateway demo](../README.md#gateway-demo)                                                                    |
| Control runtime AI                      | Try a sandbox call before and after critical approval and activation. Check the policy block, successful call, permitted models, and key history. [Gateway browser test](../e2e/gateway.spec.ts)                                                                                                                    |
| Bring unregistered usage into Inventory | Upload the sample usage CSV, save the reconciliation, register the unmatched app, and recheck. The current and original views should show zero and three unmatched calls respectively. [Outside-gateway usage](../README.md#review-usage-outside-the-gateway)                                                       |
| Keep ownership and approvals current    | Filter owner gaps, review a scheduled attestation, and export the audit chain. The 30-day ownership summary uses the first recorded Catalog observation and reports incomplete coverage. [Owner attestation](../README.md#owner-attestation) · [Portfolio reports](../README.md#portfolio-reports)                  |

## Evidence needed for a pilot

- **Foundation.** Configure target SSO and directory sync in a test tenancy, verify builder and reviewer access with managed identities, and check app ownership resolution for disabled users. Exercise the intake and review paths with representative builders to establish registration timing and satisfaction. [Deployment](../README.md#deployment-and-roadmap)
- **Gateway.** Exercise a live provider using approved synthetic prompts and isolated credentials. Capture added latency, failure behaviour, and key rotation or revocation in the intended deployment. Confirm regional hosting, provider retention, and incident ownership before handling company data. The sandbox probe provides repeatable client and Frontstage latency summaries for a synthetic workload. [Sandbox latency probe](../README.md#measure-sandbox-gateway-latency) · [Live OpenAI configuration](../README.md#live-openai-call)
- **Automation.** Select the ticketing system and hosted provider for the pilot, then verify their supported permissions and interfaces. The prototype supports linked tickets and copied review context, plus uploaded hosted inventory and outside-gateway usage reconciliations. Automatic ticket creation, provider controls, and bypass detection still require integration evidence. [Review evidence](../README.md#review-evidence) · [Hosted inventory](../README.md#reconcile-a-hosted-provider-inventory)
- **Scale.** Test the Directory decision flow with an actual destination access workflow and agree who fulfils requests. Validate co-ownership and retirement against the pilot organisation’s lifecycle policy. The prototype supports owner decisions, audit history and Engineering co-ownership. [Engineering co-ownership](../README.md#engineering-co-ownership) · [App directory](../README.md#app-directory)

[MCP setup](../README.md#read-and-register-app-records-over-mcp) · [MCP tests](../scripts/catalog-mcp.test.mjs)       | Check credential expiry, rotation and least privilege with the intended MCP client. Use a pilot identity to list an allowed record and preview a synthetic descriptor. Verify write tools are disabled by default, then enable them for an authorized identity. The local image smoke test also checks that Frontstage becomes ready after an app restart and that a synthetic registration timing row remains in PostgreSQL. It restores a logical backup to a fresh database on the same disposable PostgreSQL instance and checks readiness and row persistence again. [Image smoke test](../scripts/test-pilot-image.mjs)

For an audit restore drill, save the record and key head digests separately from the backup while the test app is quiescent. After restoring, export Audit history again before making changes. Pass the saved record head as the second argument to `yarn audit:verify` and the saved key head with `--key-head`. If the versioned export had no key events, use `--expect-no-key-events` instead. After writes resume, use the saved nonempty digests with `--checkpoint` and `--key-checkpoint` to check that the new history still includes them.

The mocked live-provider integration test also verifies that a malformed provider reply returns a generic error and leaves synthetic prompts, upstream content, and credentials out of the response and failure log. [Gateway integration test](../packages/backend/src/governance/plugin.test.ts)

### Run the pilot identity checks

Use managed test accounts and a synthetic Tier 3 app owned by the builder. Keep the deciding reviewer independent of the app. Record expected and observed results, including the delay between an identity change and its effect in Frontstage.

| Scenario                      | Pass condition                                                                                                                                                                                                                                                                                                                                                                            |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Managed sign-in and Inventory | Sign in as the builder and reviewer in separate browser sessions. Each session resolves to the expected Catalog user. The role probe confirms that both can read Inventory and only the reviewer can read registration feedback and timing. [Role probe](../README.md#check-pilot-builder-and-reviewer-access)                                                                                       |
| Review permissions            | Submit the synthetic Tier 3 app. As the builder, verify that you cannot record a review decision for it. Verify that the independent reviewer can record a decision with the required evidence. [Critical review demo](../README.md#require-evidence-for-a-critical-review)                                                                                                               |
| Review privacy                | Open the same app as an unrelated builder and confirm that review notes and evidence links are absent. The owner and independent reviewer can read them.                                                                                                                                                                                                                                  |
| Disabled user and ownership   | Disable the builder in the managed identity source. Wait for the Catalog update. Confirm that a fresh sign-in and the next session refresh are refused, and that the reviewer sees the inactive owner in **Ownership issues**. Record any difference between fresh sign-in, refresh and the lifetime of an already-issued credential. [Ownership reports](../README.md#portfolio-reports) |

## Metric scope

| Spec metric          | What the prototype measures                                                                                                                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Catalog coverage     | Tracked GitHub discoveries with a valid, source-matched, non-retired record and current Catalog ownership divided by non-dismissed tracked discoveries. The registered share is shown separately. A pilot needs to establish coverage of sources beyond GitHub.                |
| Gateway share        | Estimated live gateway spend divided by that estimate plus manually supplied outside spend for the same window. A pilot measurement needs complete billing data for both amounts.                                                                                              |
| Orphaned apps        | Current accountable-owner gaps first observed more than 30 days ago. The first observation depends on the Catalog check schedule and missing observations are reported separately.                                                                                             |
| Overdue reviews      | Non-retired Tier 2 and Tier 3 apps with an overdue scheduled review or attestation divided by non-retired Tier 2 and Tier 3 apps.                                                                                                                                              |
| Time to register     | The opt-in local measure shows the median time to submit a successful Tier 1 form and its sample count over 30 UTC calendar days. Backstage Analytics also emits timing through successful save when an analytics destination is configured.                                   |
| Time to decision     | Median UTC weekdays from first pending Tier 3 submission to the first overall approval or request for changes. Pending decisions appear in the queue.                                                                                                                          |
| Builder satisfaction | The opt-in local report shows the response rate and satisfied share for feedback offered after interactive registration over 30 UTC calendar days. The form also emits the optional three-point response through Backstage Analytics. A pilot needs a representative baseline. |

Reviewers can download CSVs from **Tier 1 registration time** and **Registration feedback**. Both include the inclusive UTC date range. The timing export includes sample count and median seconds, and the feedback export includes aggregate offer, response, and satisfied counts.

The percentages and time targets in the spec are proposals. Collect representative pilot data before using them as launch criteria.
